# 코드 설명 주석 작성

학습자가 코드의 동작뿐 아니라 설계 의도, 주요 API의 사용 규칙, 주의할 제약까지 이해할 수 있도록 주석을 작성한다. 사용자와 저장소에서 사용하는 언어를 따르며, 한국어 요청에는 자연스러운 한국어 주석을 사용한다.

## 핵심 원칙

- 사용자가 코드 변경을 함께 요청하지 않았다면 실행 코드, 타입, 스키마, 설정값과 외부 동작을 변경하지 않는다.
- 대상 파일 전체와 필요한 타입, 스키마, 설정, 주변 예제를 읽고 실제 동작을 이해한 뒤 주석을 작성한다.
- 코드나 공식 문서로 확인할 수 있는 내용만 설명하며 추측을 사실처럼 단정하지 않는다.
- 유용한 기존 주석과 저장소의 형식은 유지하되, 중복되거나 오래되었거나 현재 구현과 맞지 않는 주석은 고친다.
- 코드만 읽어도 분명한 내용을 반복하기보다 코드에서 바로 드러나지 않는 이유, 규칙, 제약과 결과를 설명한다.

## 작업 흐름

1. 함수의 경계와 주요 처리 흐름을 파악한다.
2. 설명이 필요한 함수, API 호출, 옵션과 조건을 선택한다.
3. 설명 대상과 가까운 위치에 간결한 주석을 추가하거나 기존 주석을 다듬는다.
4. 주석이 실제 동작과 일치하고 같은 설명을 반복하지 않는지 검토한다.
5. 실행 코드가 변경되지 않았는지 확인하고, 가능한 경우 포매터와 타입 검사 또는 문법 검사를 실행한다.

## 주석 선택과 배치

### 함수 설명

중요한 함수 위에는 JSDoc을 사용한다. 필요한 내용만 골라 설명한다.

- 함수가 수행하거나 보여 주는 작업
- 이 방식을 사용하는 이유와 적절한 사용 시점
- 중요한 관계, 트랜잭션, 부수 효과와 반환값의 특징
- 선행 조건, 제약과 실패 가능성

파일이 순서대로 실행되는 예제나 튜토리얼일 때만 함수 설명에 번호를 붙인다. 함수의 전체 목적과 함수 내부의 세부 API 설명을 반복하지 않는다.

```ts
/**
 * 2) 중첩 생성: User와 Post를 한 번에 생성
 *
 * 관계 데이터도 함께 만들어야 할 때 사용하는 중첩 쓰기 예제입니다.
 * include를 지정하면 생성된 User와 Post를 하나의 결과로 받을 수 있습니다.
 */
```

### 주요 코드 설명

다음 내용은 해당 코드 바로 위에 두세 문장의 짧은 주석 블록으로 설명한다.

- ORM, SDK, 프레임워크, 파일 시스템, 네트워크와 데이터베이스의 주요 작업
- `data`, `select`, `include`, `where`, `connect`, `createMany` 같은 중요한 옵션
- 기본값, 자동 생성값, 고유 제약, 외래 키와 연쇄 삭제 동작
- 반환 형태, 부수 효과, 오류 처리, 자원 정리와 해제
- 여러 API 형태 중 현재 방식을 선택한 이유
- 특정 조건에 의존하는 선행 조건과 실패 가능성

```ts
// connect는 새 User를 만들지 않고 기존 User와 연결합니다.
// where에는 id나 email처럼 값이 고유한 필드를 지정해야 합니다.
author: {
  connect: { email: authorEmail },
},
```

문법을 그대로 읽어 주는 설명은 피한다. 예를 들어 `createMany`에는 생성된 객체가 아니라 처리 건수를 반환하고 중첩 쓰기를 지원하지 않는다는 사용 규칙을 설명할 수 있다. 반면 “title에 제목을 넣습니다.”처럼 코드에서 바로 알 수 있는 내용은 주석으로 작성하지 않는다.

## 자연스러운 한국어

- `합니다`, `됩니다` 같은 완결된 문장과 평이한 설명체를 일관되게 사용한다.
- 영어 원문의 어순이나 명사 나열을 그대로 옮기지 말고 문맥에 맞는 자연스러운 한국어로 고친다.
- 주어나 서술어가 생략되어 뜻이 불분명한 기존 주석은 기술적 의미를 유지하면서 완전한 문장으로 보완한다.
- 실제 동작을 먼저 설명하고, 정확성을 높이는 데 필요한 경우에만 전문 용어를 사용한다.
- 코드의 API 이름이나 옵션명은 그대로 표시하되, 주변 설명은 자연스러운 한국어로 작성한다.

용어는 설명하는 대상에 맞게 구체적으로 선택한다.

- 실행 중 입력값을 검증하는 규칙은 `스키마`라고 한다.
- TypeScript가 컴파일할 때 검사하는 대상은 `타입`이라고 한다.
- HTTP 본문이나 매개변수의 형태는 `요청 구조`, `응답 구조` 또는 `요청·응답 구조`라고 한다.
- 라우트의 입력, 출력과 상태 코드까지 포함한 외부 동작은 `API 명세`라고 한다.

예를 들어 “TypeBox 계약을 정의합니다”보다는 “TypeBox로 요청·응답 스키마를 정의합니다” 또는 “TypeBox 스키마에서 타입을 생성합니다”라고 쓴다. 제공자와 사용자가 함께 지켜야 하는 호환성의 의미가 핵심일 때만 `계약`이라는 용어를 사용하고, 처음 나올 때 그 의미를 함께 설명한다.

## 피해야 할 주석

- 모든 줄, import, 단순 할당과 로그문에 붙인 자명한 설명
- 코드의 문법이나 변수 이름을 그대로 풀어 읽은 설명
- JSDoc과 함수 내부에서 반복되는 같은 설명
- 확인하지 않은 동작, 반환값과 실패 조건에 대한 단정
- 한 블록에 서로 관련 없는 여러 주제를 담은 긴 설명

## 완료 전 점검

- 중요한 함수의 목적과 주요 API의 사용 규칙이 필요한 위치에 설명되어 있는가?
- 모든 주석이 현재 코드의 동작과 일치하는가?
- 어색한 번역투, 빠진 문장 성분과 불완전한 문장이 남아 있지 않은가?
- 중복되거나 자명한 주석이 과도하게 추가되지 않았는가?
- 실행 코드가 보존되었고 검증 과정에서 새로운 오류가 발견되지 않았는가?
